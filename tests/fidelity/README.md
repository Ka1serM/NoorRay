# MaterialX SVM fidelity corpus

This is NoorRay's equivalent of Material Fidelity's renderer comparison flow.
Every case renders one authored MaterialX document through an independent
MaterialX reference backend and through NoorRay's SVM path, then records
renderer-specific output and image metrics.

The reference must be generated by MaterialXView GLSL, MaterialX OSL, or an
equivalent independent implementation.  Never use a NoorRay render as a
reference: the point is to expose errors in the SVM implementation.

The fixture scene must match the reference's geometry, camera, environment,
colour transform, and resolution.  This is mandatory for a meaningful image
diff.  Material Fidelity's published contract is a useful default: a shader
ball centered at the origin, perspective camera at `(0,0,5)` with 45 degree
FOV, fixed 512-square output, no tone map, sRGB output, and its fixed IBL.

For a checked-in reference image, create a manifest such as:

```json
[
  {
    "name": "noise3d_float",
    "scene": "/absolute/path/to/noorray-noise3d.nrscene",
    "reference": "/absolute/path/to/materialx-glsl.png"
  }
]
```

To run MaterialXView and NoorRay side by side, omit `reference` and provide
the MaterialX document and matching fixture mesh instead:

```json
[
  {
    "name": "open_pbr_shaderball",
    "scene": "/absolute/path/to/noorray-open-pbr.nrscene",
    "material": "/absolute/path/to/material.mtlx",
    "mesh": "/absolute/path/to/shaderball.glb",
    "environment": "/absolute/path/to/san_giuseppe_bridge.hdr"
  }
]
```

Then run:

```sh
python3 tests/fidelity/materialx_fidelity.py \
  --manifest tests/fidelity/cases.json \
  --noorray build/release/NoorRay \
  --output build/materialx-fidelity --spp 1024
```

With the vendored viewer built in `build/materialxview`:

```sh
python3 tests/fidelity/materialx_fidelity.py \
  --manifest tests/fidelity/cases.json \
  --materialxview build/materialxview/bin/MaterialXView \
  --materialx-root external/materialx \
  --noorray build/release/NoorRay --xvfb
```

Each generated case writes `materialxview.png`, `noorray.png`,
`absdiff_x8.png`, and `metrics.json`; the root writes `summary.json`.
`psnr_db`, `mae_8bit`, and `max_error_8bit` make regressions sortable, while
the magnified absolute-difference image identifies the affected MaterialX
node semantics.

Build the vendored reference viewer in an isolated build tree (the main
NoorRay configuration intentionally keeps the interactive viewer disabled):

```sh
cmake -S external/materialx -B build/materialxview -G Ninja \
  -DCMAKE_BUILD_TYPE=Release -DMATERIALX_BUILD_VIEWER=ON \
  -DMATERIALX_BUILD_RENDER=ON -DMATERIALX_BUILD_RENDER_PLATFORMS=ON \
  -DMATERIALX_BUILD_GEN_GLSL=ON -DMATERIALX_BUILD_GEN_OSL=OFF \
  -DMATERIALX_BUILD_GEN_MDL=OFF -DMATERIALX_BUILD_TESTS=OFF
cmake --build build/materialxview --target MaterialXView -j 8
```

The viewer needs an X11/OpenGL development environment (`libXt-devel` on
Fedora).  It can be launched alongside NoorRay by the fidelity script; both
renders are saved before the image diff is calculated.

The canonical NoorRay test is the C++ Catch2 test, which uses the copied
MaterialX validation fixtures under `tests/assets/materialx/validator` and
requires no environment-variable setup:

```sh
build/release/tests/materialx_fidelity_test
```

It renders the checked-in materials through MaterialXView and the matching
NoorRay scenes, then compares the resulting bitmaps. The Python runner is
still useful for expanding the corpus interactively, but is not required by
the NoorRay test suite.
